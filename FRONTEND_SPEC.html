Voice Agent Platform — Frontend Specification

The single reference you build the Vocera web app from. Every endpoint below is live and tested — treat it as ready to call. You build the UI and wire it up; the backend is done.

For Frontend Developer Version 3 — supersedes the v2 PDF Scope Client dashboard · Agent builder · Admin

Your scope this round: the Client dashboard (/app), the Agent builder (/onboarding), and the Admin panel (/admin) — including the new Campaigns, Instant Calls, WhatsApp and Operations Center areas.

Out of scope: the public marketing site / landing page (/). It's owned separately and already built — described only for context.

01What you're building

A web app with three separate portals:

PortalWhoRouteLogin?Your scope
Public siteAnyone/NoOut of scope
Client dashboardPaying clients/appYesYes
Agent builderNew + returning clients/onboardingYesYes
Admin panelPlatform owner (us)/adminYesYes

Product in one line: businesses get an AI voice agent that answers their phone calls in English/Hindi/Hinglish (and other Indic languages), answers from their own knowledge base, captures qualified leads, hands off to a human when needed, runs outbound calling campaigns, and can send WhatsApp brochures/confirmations.

02Tech stack

  • React + TanStack Router — file-based routes in frontend/src/routes
  • Tailwind CSS
  • Recharts for charts
  • fetch for API calls (a thin lib/api wrapper handles the token + 401)
  • Supabase JS SDK for auth (Section 4)
  • Web Audio API (AudioContext + AudioWorklet) for the browser voice test call — plumbing already exists in lib/webcall.ts + useVoiceCall.ts; reuse it.

03Talking to the backend

  • Dev base URL: http://localhost:3000 (the UI runs on :8080 and calls the API).
  • All responses JSON. Authenticated requests send Authorization: Bearer <token>.
  • Errors: { "error": "message" } with HTTP 400 / 401 / 403 / 404 / 500.
  • Handle 401 by clearing the token and redirecting to the right login page.
  • Phone numbers are E.164 (+918071583556). A national 08071583556 fails at the carrier — validate on input.

04Authentication

Use the Supabase JS SDK for login — it handles tokens. Two methods:

Password login

POST/api/auth/login{ email, password } → { token, role, tenant_id }

Google Sign-In

POST/api/auth/google{ credential } → { token, role, tenant_id, is_new }
  • is_new: true → first login; route to /onboarding to set up the business.
  • is_new: false → existing user; route by role.
  • A <GoogleSignInButton /> component already exists — reuse it.

Routing after auth: role === "admin" → /admin; otherwise → /app (or /onboarding if is_new). Store the token, attach it to every call, and on 401 clear + redirect. You never pass user/tenant IDs — the token encodes them.

Two login pages: /login (clients — Google + password) · /admin-login (admin — password).

Signup is public and Google-only (/signup). A legacy email/password endpoint still exists if ever needed:

POST/api/signup{ email, password, business_name } → { success, tenant_id, message }

05Public site — out of scope

Already built by another owner. For context only: the marketing site (hero, features, pricing, contact form) plus a live voice demo — visitors actually talk to a real AI agent in the browser ("Talk to Priya" + per-industry demos). The old scripted/animated chat demo is gone. You don't build or change this. Its two public endpoints are in Section 13 for completeness.

Per-caller data the agent fetches at call time (order status, dues, booking). Backed by the client's REST API (http) or a data sheet uploaded here (table). A LiveDataSetup.tsx component already exists.

Step 4 — Test the call (browser — no phone)

This is the showpiece of the builder — make it feel like a real phone call. The client talks and hears the agent, running the exact same Gemini Live engine + knowledge base as a real call.

Real voice test (primary) — over a WebSocket:

WSws://<host>/test-stream
→ send  { event:"start", start:{ token:<bearer>, config?:<draft config>, streamSid? } }
→ send  { event:"media", media:{ payload:<base64 PCM audio> } }   // mic, continuously
← recv  audio frames (agent speech) + { event:"started" } / { event:"clear" } (barge-in) / { event:"error" }
→ send  { event:"stop" }
  • Pass the draft config to test unsaved changes; omit to test the saved config.
  • Mic→PCM, AudioWorklet playback and barge-in already exist in webcall.ts + useVoiceCall.ts + VoiceTester.tsx. Reuse the VoiceTester component — a phone-style UI with a talk button + live status.

Text-chat test (fallback) — same AI + KB pipeline, typed:

POST/api/client/agent/test{ message, session_id, config? } → { reply, used_knowledge }
POST/api/client/agent/test/reset{ session_id } → { success }

Show a small badge when used_knowledge: true (proves the KB works). "Reset conversation" clears memory.

Step 5 — Publish

POST/api/client/agent/publish→ { success, status:"published" }

After publish: success state ("Your agent is live! Calls to your number will now be handled by your AI agent.") and flip the badge Draft → Live.

08Campaigns NEW — /app/campaigns

Outbound calling. A campaign dials a list of contacts with either an AI agent (type: "ai_sales" — full Gemini conversation) or a fixed spoken message (type: "template"). Contacts come from: file upload, paste, Google Sheet, database query, or a real-time webhook (CRM / Meta & Google Lead Ads).

Campaigns require Redis on the backend. If it's off, start returns 503 — surface that gracefully.

09Instant Calls NEW — /app/instant

A standalone "CRM entry → immediate AI call" webhook (not a campaign). The moment a new lead lands in the client's CRM, they POST it to their ingress URL and we dial within seconds.

GET/api/client/instant-call→ { enabled, url, token, header, presets[], active_preset, from_number, skip_recent_days, skip_statuses[] }
PUT/api/client/instant-call{ enabled?, preset?, from_number?, skip_recent_days?, skip_statuses? }
POST/api/client/instant-call/rotate→ new token

UI: on/off toggle · the ingress URL + token (copy + rotate) · a preset dropdown · a caller-ID (from_number, E.164) · de-dup guards: skip_recent_days (don't re-call within N days) + skip_statuses (lead statuses that mean "already worked" — a tag/multiselect).

10WhatsApp NEW — /app/whatsapp

The agent can send a brochure or a booking confirmation over WhatsApp. Messages send from the platform's shared WhatsApp number — the client sets no API credentials, only what shows in the message (their contact number) and which files to send.

GET/api/client/whatsapp→ { platform_enabled, enabled, display_phone, own_number, provider, phone_number, phone_number_id, token_set, templates }
PUT/api/client/whatsapp{ enabled?, display_phone?, /* advanced BYO-number… */ }
  • platform_enabled tells you the shared sender is live (show a "ready" state). If false, show "WhatsApp not yet configured by Vocera".
  • Main UI: enable toggle + contact number to display. Put BYO-number fields (provider, phone number id, token, template names) behind an "Advanced" disclosure. Never display the token back (token_set just says one is saved).

Sendable documents (brochures/menus — own store, separate from the knowledge base):

GET/api/client/whatsapp/documents→ [ { id, topic, filename, mime_type, size_bytes, created_at } ]
POST/api/client/whatsapp/documentsmultipart file + topic
PUT/api/client/whatsapp/documents/:id{ topic }
DELETE/api/client/whatsapp/documents/:id

UI: upload a file + a topic label (e.g. "3BHK brochure", "menu"), list them, edit topic, delete.

12Operations Center NEW — /admin/ops/*

A real-time observability console for the voice platform. 15 sections. Every REST endpoint is the initial snapshot / polling fallback; live deltas stream over a WebSocket.

Live feed WebSocket:

WSws://<host>/ops-stream?token=<admin bearer>
← { type:"snapshot", snapshot, calls }   // on connect + every 5s heartbeat
← { type:"event", event, payload }        // live deltas
← { type:"error", error:"unauthorized" }  // then closes

The browser can't set headers on a WS handshake, so the admin token is passed as ?token=.

15Build order

  1. Auth + shell — Google + password login, token handling, protected routes, the two sidebars.
  2. Agent builder (/onboarding) — the client's first experience. Highest priority. Nail the voice test call (Step 4).
  3. Client dashboard — Overview → Calls (inbound/outbound) → Call detail → Leads.
